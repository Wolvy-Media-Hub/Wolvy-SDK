# Wolvy-SDK

The files served at **sdk.wolvy.net**: scripts that customers load on their own pages.

| SDK | Address | Docs |
|---|---|---|
| Player API (`WolvyPlayer`) | `https://sdk.wolvy.net/player/v1/wolvy-player.js` | https://docs.wolvy.net/player-api/ |

## How it is hosted

A Cloudflare Worker named `wolvy-sdk` that holds **files only, no code**, attached to the custom
domain `sdk.wolvy.net` (zone `wolvy.net`). Cloudflare serves a file without running a Worker, so
these requests are free, unlimited and never count against the Workers request quota. That stays
true as long as `wrangler.jsonc` has no `"main"` and Workers Cache is not switched on.

Limits that do apply: 25 MiB per file, 20,000 files, 100 rules in `public/_headers`.

## Addresses

Every SDK has its own folder, and every release two addresses:

| Address | Changes? | Browser cache |
|---|---|---|
| `/player/v1/wolvy-player.js` | Follows the newest 1.x release | 1 hour |
| `/player/1.0.0/wolvy-player.js` | Never | 1 year, immutable |

A customer who wants to lock a page to one release uses the second form (it also works with
`integrity="sha384-…"`). A breaking change gets a new major: `v2`, and `v1` stays as it was.

## Layout

| Path | What |
|---|---|
| `src/<sdk>/` | The source you edit |
| `sdks.json` | Each SDK's current version and file list |
| `public/` | Exactly what is served. Committed, because old versions must stay available: each deploy replaces the whole set of files |
| `public/_headers` | Generated by `npm run release`. Do not edit |
| `public/_redirects` | `/` goes to the docs |
| `scripts/release.mjs` | Copies `src/` into `public/` and refuses to change a version that is already published |
| `wrangler.jsonc` | The Cloudflare deployment |

## Release a change

1. Edit the file in `src/<sdk>/`, and raise the version **inside the file** (`WolvyPlayer.version`).
2. Set the same version in `sdks.json`.
3. `npm run release` writes `public/<sdk>/<version>/`, updates `public/<sdk>/v<major>/` and `public/_headers`.
4. Commit, then `npm run deploy` (checks `public/` is up to date, then `npx wrangler deploy`; the first run asks you to sign in to Cloudflare).

Keep `.js` and `.css` files plain ASCII (write other characters as `\uXXXX`): they are served
without a `charset`, so a browser reads them in the encoding of the page that loads them.

## Add another SDK

1. Put its files in `src/<name>/` and add `"<name>": { "version": "1.0.0", "files": [...] }` to `sdks.json`.
2. Release and deploy as above. It is served at `/<name>/v1/…` and `/<name>/1.0.0/…`.

Files that are not fetched by a browser (an npm tarball, a JSON manifest, an Android `.aar`):
Cloudflare's bot rules on `wolvy.net` block automated clients on every file type except the
common static ones (`.js`, `.css`, images, fonts, `.txt`). Before publishing such a file, add
`sdk.wolvy.net` to the WAF rule "Public pages - let crawlers and AI read".

## The Player API SDK and the player

`src/player/wolvy-player.js` is one half of the Player API. The other half, `wolvyPlayerApi`, runs
inside the player page and lives in `Wolvy-Worker-Script/worker.js`. They talk over `postMessage`
(`type: 'wolvy:player', v: 1`). A new method or event has to be added on both sides.

The SDK is the only Wolvy code that runs inside a customer's own page rather than inside the
player iframe, so whoever can deploy this project can run script on customers' sites. Keep deploy
access to the `wolvy-sdk` Worker as tight as access to the player Worker.
