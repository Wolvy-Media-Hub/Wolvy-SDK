# Wolvy-SDK

The files served at **sdk.wolvy.net** (scripts that customers load on their own pages), and the npm
packages built from them.

| SDK | Address | npm | Docs |
|---|---|---|---|
| Player API (`WolvyPlayer`) | `https://sdk.wolvy.net/player/v1/wolvy-player.js` | `@wolvy/player` | https://docs.wolvy.net/player-api/ |
| Player API for React (`<WolvyPlayer>`, `useWolvyPlayer`) | not served | `@wolvy/player-react` | same |

Licensed under the Apache License 2.0 (`LICENSE`; each npm package carries its own copy). Public repository: https://github.com/Wolvy-Media-Hub/Wolvy-SDK.

## How it is hosted

A Cloudflare Worker named `wolvy-sdk` that holds **files only, no code**, attached to the custom
domain `sdk.wolvy.net` (zone `wolvy.net`). Cloudflare serves a file without running a Worker, so
these requests are free, unlimited and never count against the Workers request quota. That stays
true as long as `wrangler.jsonc` has no `"main"` and Workers Cache is not switched on.

Limits that do apply: 25 MiB per file, 20,000 files, 100 rules in `public/_headers`.

## Addresses

Every SDK has its own folder, and every release two addresses:

| Address | Changes? | Browser cache |
|---|---|---|
| `/player/v1/wolvy-player.js` | Follows the newest 1.x release | 1 hour |
| `/player/1.0.0/wolvy-player.js` | Never | 1 year, immutable |

A customer who wants to lock a page to one release uses the second form (it also works with
`integrity="sha384-…"`). A breaking change gets a new major: `v2`, and `v1` stays as it was.

## Layout

| Path | What |
|---|---|
| `src/<sdk>/` | The source you edit. `src/player/` holds `wolvy-player.js` and its types, `wolvy-player.d.ts` |
| `sdks.json` | Each SDK's current version, the files served, and (`npm`) the npm package that ships them |
| `public/` | Exactly what is served. Committed, because old versions must stay available: each deploy replaces the whole set of files |
| `public/_headers` | Generated by `npm run release`. Do not edit |
| `public/_redirects` | `/` goes to the docs |
| `packages/player/` | The npm package `@wolvy/player`. `wolvy-player.js` and `wolvy-player.d.ts` are copied here by `npm run release`: never edit them here. `package.json`, `README.md` and `LICENSE` are edited here |
| `packages/player-react/` | The npm package `@wolvy/player-react`. The source is `index.js` (an ES module, no JSX) and `index.d.ts`; `index.cjs` and `index.d.cts` are generated from them by `npm run release` |
| `scripts/release.mjs` | The one release step: copies `src/` into `public/` and into the npm packages, generates the CommonJS files, and refuses to change a version that is already published |
| `test/` | `npm test`: the React component in a simulated browser, the type declarations, the release rules |
| `package.json` | Private, named `wolvy-sdk`. npm workspaces for `packages/*`, and the tools the tests need |
| `wrangler.jsonc` | The Cloudflare deployment. Only `public/` is uploaded |

## The rule for npm

For a given version, `wolvy-player.js` in the npm package and the file at
`sdk.wolvy.net/player/<version>/wolvy-player.js` are **the same bytes**. That is how it is kept true:

- The package's copy is written only by `npm run release`, from `src/player/`, in the same run that
  writes `public/player/<version>/`. The package's `version` is set from `sdks.json` in that run.
- `npm run check` (and so `npm run deploy`) compares `packages/player/wolvy-player.js` with
  `public/player/<version>/wolvy-player.js` on disk and fails if they differ, if the package's
  version is not the one in `sdks.json`, if `package.json` `files` leaves the file out, or if the
  React package's CommonJS files are out of date.
- Each package's `prepublishOnly` runs `scripts/release.mjs --publish`: the same check, plus a real
  `repository` in its `package.json`. `npm publish` stops if either fails.
- `npm test` packs both packages with `npm pack` and compares the `wolvy-player.js` inside the
  tarball with the served file, and checks that `/player/1.0.0/` still has the bytes deployed on
  2026-11-17.

One version number covers both: a change to the types alone is a new release of the SDK too (raise
the version in `wolvy-player.js` and `sdks.json`), since npm never accepts the same version twice.

## Release a change

1. Edit the file in `src/<sdk>/`, and raise the version **inside the file** (`WolvyPlayer.version`).
   A new method or event goes into `wolvy-player.d.ts` as well (`npm test` compares the two).
2. Set the same version in `sdks.json`.
3. `npm run release` writes `public/<sdk>/<version>/`, updates `public/<sdk>/v<major>/` and
   `public/_headers`, copies the files into `packages/<sdk>/` and sets that package's version.
4. `npm test`, then commit (including `packages/`).
5. `npm run deploy` (checks that `public/` and `packages/` are up to date, then `npx wrangler deploy`;
   the first run asks you to sign in to Cloudflare).
6. Publish to npm (below), after the deploy, so the npm version is never ahead of sdk.wolvy.net.

Keep `.js` and `.css` files plain ASCII (write other characters as `\uXXXX`): they are served
without a `charset`, so a browser reads them in the encoding of the page that loads them.

`@wolvy/player-react` has its own version, in `packages/player-react/package.json`. After editing
`index.js` or `index.d.ts`, run `npm run release` (it regenerates `index.cjs` and `index.d.cts`),
raise that version, and publish it. `index.js` is converted to CommonJS by a small text rewrite, so
it may only use `import * as X from '…';`, `import X from '…';`, `export function` and
`export const` at the start of a line; the release step refuses anything else.

## Publish to npm

`@wolvy/player` 1.0.0 and `@wolvy/player-react` 1.0.0 were published on 2026-11-19 from `main`
(`57a4456`), under the npm organisation `wolvy`, and tagged `player-v1.0.0` and
`player-react-v1.0.0`. Publishing needs an account with publish rights in that organisation; npm
asks for a browser approval (two-factor) on every publish.

For a new version, from the repository root, after `npm ci`, `npm test` and the deploy:

```sh
npm publish --workspace packages/player          # @wolvy/player, first
npm publish --workspace packages/player-react    # @wolvy/player-react, if it changed
```

`publishConfig.access` is `public` in both packages. A published npm version cannot be replaced; a
mistake is fixed by a new version (and `npm deprecate` on the bad one).

## Tests

```sh
npm install     # once: TypeScript 5 and 7, React, React DOM, @types/react, jsdom (Node 22.22 or later)
npm test        # node --test; needs no network
```

| File | What it proves |
|---|---|
| `test/player-react.test.mjs` | The component and the hook in jsdom against a fake player speaking the postMessage protocol, from the ES module and from the CommonJS file: the iframe attributes, ready, all 12 event props, origin and source checks, cleanup on unmount and on a new `src`, StrictMode, `loading="lazy"` |
| `test/player-react-ssr.test.mjs` | Importing and rendering to HTML on a server, with no `window` |
| `test/player-package.test.mjs` | `import` and `require` of `@wolvy/player`; the declaration file names exactly the methods, events and error codes of the class |
| `test/types.test.mjs` | `tsc --noEmit` on the usage examples in `test/types/` (a bundler project, Node ESM, Node CommonJS, a plain script), with TypeScript 5 and 7. Lines marked `@ts-expect-error` must fail |
| `test/release.test.mjs` | `npm run check`; the bytes of `/player/1.0.0/`; `npm pack` contents against the served file; tampered copies of the repository fail the check |

## Add another SDK

1. Put its files in `src/<name>/` and add `"<name>": { "version": "1.0.0", "files": [...] }` to `sdks.json`.
2. Release and deploy as above. It is served at `/<name>/v1/…` and `/<name>/1.0.0/…`.
3. To ship it on npm too, create `packages/<name>/` (a `package.json` with `"files"` listing the
   served files, a README, the LICENSE) and add `"npm": { "folder": "packages/<name>", "extraFiles": [...] }`
   to its entry in `sdks.json`; `extraFiles` are files from `src/<name>/` that npm ships but the host
   does not serve, such as type declarations.

Files that are not fetched by a browser (an npm tarball, a JSON manifest, an Android `.aar`):
Cloudflare's bot rules on `wolvy.net` block automated clients on every file type except the
common static ones (`.js`, `.css`, images, fonts, `.txt`). Before publishing such a file, add
`sdk.wolvy.net` to the WAF rule "Public pages - let crawlers and AI read". (The npm packages are
served by the npm registry, not by sdk.wolvy.net, so they do not need this.)

## The Player API SDK and the player

`src/player/wolvy-player.js` is one half of the Player API. The other half, `wolvyPlayerApi`, runs
inside the player page and lives in `Wolvy-Worker-Script/worker.js`. They talk over `postMessage`
(`type: 'wolvy:player', v: 1`). A new method or event has to be added on both sides, and to
`src/player/wolvy-player.d.ts`.

The SDK is the only Wolvy code that runs inside a customer's own page rather than inside the
player iframe, so whoever can deploy this project, or publish `@wolvy/player` and
`@wolvy/player-react` to npm, can run script on customers' sites. Keep deploy access to the
`wolvy-sdk` Worker and publish rights on the npm organisation as tight as access to the player
Worker (two-factor authentication on the npm accounts).
